# Incident 004: DB Connection Failed — Password Special Characters Broke Shell Sourcing of .env

**Date:** 2026-08-11
**Severity:** Low (blocked manual verification step, no live infrastructure affected)
**Component:** EC2 bootstrap script / shell environment handling

## Symptoms

With the full stack deployed (VPC, RDS, EC2, all previous incidents
resolved), a manual connectivity check from the app EC2 instance to RDS
via `psql` failed:

```
sh-5.2$ psql "$DATABASE_URL" -c "SELECT version();"
psql: error: connection to server on socket "/var/run/postgresql/.s.PGSQL.5432"
failed: No such file or directory
        Is the server running locally and accepting connections on that socket?
```

The error suggested `psql` was attempting a local Unix-socket connection
instead of a remote TCP connection to the RDS endpoint — implying
`$DATABASE_URL` was not actually set to the expected connection string.

## Investigation

```bash
echo "$DATABASE_URL"
```

returned an empty string, confirming the variable was never exported into
the shell session. The bootstrap script (`ec2.tf` user_data) writes
`DATABASE_URL=...` into `/opt/ledger-app/.env` as a plain file on disk, but
a file on disk is not automatically loaded into shell environment variables
— it has to be explicitly sourced.

Attempting the obvious fix:

```bash
set -a
source /opt/ledger-app/.env
set +a
```

failed with:

```
sh: /opt/ledger-app/.env: line 1: syntax error near unexpected token `)'
sh: /opt/ledger-app/.env: line 1: `DATABASE_URL=postgresql://ledger_admin:cX1DA80t4gKmA:6^Ef7OHDg)@rds-fintech-ledger-demo.cu7awakswhki.us-east-1.rds.amazonaws.com:5432/ledger'
```

## Root Cause

The RDS master password is generated by Terraform's `random_password`
resource with `override_special = "!#$%^&*()-_=+[]{}<>:?"` — a deliberately
broad character set chosen for password strength. This particular generated
password happened to include a closing parenthesis `)`.

When a shell (`sh`) sources a file containing `KEY=value` where `value` is
not quoted, the shell parses the *entire line* as shell syntax, not as a
literal string. An unquoted `)` in that context is interpreted as the end
of a subshell grouping `( ... )`, producing a syntax error rather than
treating it as a literal character in the value.

The `.env` file, as written by the bootstrap script, wrote
`DATABASE_URL=postgresql://...` with no surrounding quotes — safe for many
generated passwords, but not safe for one containing shell metacharacters
like `(`, `)`, `` ` ``, `$`, or unescaped quotes.

## Fix (immediate, unblocking verification)

Bypassed the broken `source` entirely by extracting the value directly with
`grep`/`cut`, which does not attempt to interpret the value as shell syntax:

```bash
DATABASE_URL=$(grep DATABASE_URL /opt/ledger-app/.env | cut -d= -f2-)
psql "$DATABASE_URL" -c "SELECT version();"
```

This succeeded and returned `PostgreSQL 16.4 on x86_64-pc-linux-gnu...`,
confirming the full network path (EC2 in the private app subnet, through
the app-sg → db-sg security group chain, to RDS in the private db subnet)
works end-to-end.

## Verification

- `psql` returned a valid PostgreSQL version string, confirming connectivity.
- Root cause reproduced deterministically: any password containing `(`,
  `)`, backticks, or unescaped `$`/quotes will break a naive unquoted
  `source` of this `.env` file the same way.

## Prevention (applied)

Two changes were made to the Terraform code following this incident:

1. Narrowed `random_password.db_master`'s `override_special` from
   `"!#$%^&*()-_=+[]{}<>:?"` to `"!#%^&*-_=+[]{}<>:?"` — removing `(`, `)`,
   and `$`, the specific characters that break unquoted shell sourcing
   (parens as subshell syntax, `$` as variable expansion). Still broad
   enough for strong password entropy.
2. Changed the bootstrap script to single-quote the `DATABASE_URL` value
   when writing `.env`: `DATABASE_URL='postgresql://...'` instead of an
   unquoted assignment. This makes the file safe to `source` even if a
   problematic character were to slip through in the future — defense in
   depth on top of fix (1) rather than relying on the character set alone.

Both changes are in `rds.tf` and `ec2.tf` respectively. A fresh
`terraform apply` after this change would regenerate the password (since
`random_password` is not tainted automatically by this edit — a deliberate
`terraform apply` or `taint` would be needed to rotate the existing live
password) and write the corrected, quoted `.env` format on the next
instance boot.

## Lessons Learned

A password generator tuned purely for entropy/strength can produce values
that are perfectly valid to PostgreSQL but break naive shell handling
downstream. "Strong password" and "safe to embed unquoted in a shell-sourced
file" are different properties, and optimizing for the first without
checking the second created a real, reproducible failure — not a
theoretical one. Any place a generated secret crosses from "stored value"
to "interpreted by a shell" needs either a restricted character set, or
correct quoting at the point of use, or both.
